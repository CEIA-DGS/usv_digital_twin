There are myriads of \href{https://json.org}{\texttt{ JSON}} libraries out there, and each may even have its reason to exist. Our class had these design goals\+:


\begin{DoxyItemize}
\item {\bfseries{Intuitive syntax}}. In languages such as Python, JSON feels like a first class data type. We used all the operator magic of modern C++ to achieve the same feeling in your code. Check out the examples below and you\textquotesingle{}ll know what I mean.
\item {\bfseries{Trivial integration}}. Our whole code consists of a single header file \href{https://github.com/nlohmann/json/blob/develop/single_include/nlohmann/json.hpp}{\texttt{ {\ttfamily json.\+hpp}}}. That\textquotesingle{}s it. No library, no subproject, no dependencies, no complex build system. The class is written in vanilla C++11. All in all, everything should require no adjustment of your compiler flags or project settings.
\item {\bfseries{Serious testing}}. Our code is heavily \href{https://github.com/nlohmann/json/tree/develop/tests/src}{\texttt{ unit-\/tested}} and covers \href{https://coveralls.io/r/nlohmann/json}{\texttt{ 100\%}} of the code, including all exceptional behavior. Furthermore, we checked with \href{https://valgrind.org}{\texttt{ Valgrind}} and the \href{https://clang.llvm.org/docs/index.html}{\texttt{ Clang Sanitizers}} that there are no memory leaks. \href{https://github.com/google/oss-fuzz/tree/master/projects/json}{\texttt{ Google OSS-\/\+Fuzz}} additionally runs fuzz tests against all parsers 24/7, effectively executing billions of tests so far. To maintain high quality, the project is following the \href{https://bestpractices.coreinfrastructure.org/projects/289}{\texttt{ Core Infrastructure Initiative (CII) best practices}}.
\end{DoxyItemize}

Other aspects were not so important to us\+:


\begin{DoxyItemize}
\item {\bfseries{Memory efficiency}}. Each JSON object has an overhead of one pointer (the maximal size of a union) and one enumeration element (1 byte). The default generalization uses the following C++ data types\+: {\ttfamily std\+::string} for strings, {\ttfamily int64\+\_\+t}, {\ttfamily uint64\+\_\+t} or {\ttfamily double} for numbers, {\ttfamily std\+::map} for objects, {\ttfamily std\+::vector} for arrays, and {\ttfamily bool} for Booleans. However, you can template the generalized class {\ttfamily \doxylink{classbasic__json}{basic\+\_\+json}} to your needs.
\item {\bfseries{Speed}}. There are certainly \href{https://github.com/miloyip/nativejson-benchmark\#parsing-time}{\texttt{ faster JSON libraries}} out there. However, if your goal is to speed up your development by adding JSON support with a single header, then this library is the way to go. If you know how to use a {\ttfamily std\+::vector} or {\ttfamily std\+::map}, you are already set.
\end{DoxyItemize}

Note that without appending the {\ttfamily \+\_\+json} suffix, the passed string literal is not parsed, but just used as JSON string value. That is, {\ttfamily json j = "{}\{ \textbackslash{}"{}happy\textbackslash{}"{}\+: true, \textbackslash{}"{}pi\textbackslash{}"{}\+: 3.\+141 \}"{}} would just store the string {\ttfamily "{}\{ "{}happy"{}\+: true, "{}pi"{}\+: 3.\+141 \}"{}} rather than parsing the actual object.

The string literal should be brought into scope with {\ttfamily using namespace nlohmann\+::literals;} (see \href{https://json.nlohmann.me/api/operator_literal_json/}{\texttt{ {\ttfamily json\+::parse()}}}).

To implement your own SAX handler, proceed as follows\+:


\begin{DoxyEnumerate}
\item Implement the SAX interface in a class. You can use class {\ttfamily nlohmann\+::json\+\_\+sax\texorpdfstring{$<$}{<}json\texorpdfstring{$>$}{>}} as base class, but you can also use any class where the functions described above are implemented and public.

\end{DoxyEnumerate}

\hypertarget{md_build_2dt__core_2__deps_2nlohmann__json-src_2README_autotoc_md1776}{}\doxysubsubsection{\texorpdfstring{Implicit conversions}{Implicit conversions}}\label{md_build_2dt__core_2__deps_2nlohmann__json-src_2README_autotoc_md1776}
Supported types can be implicitly converted to JSON values.

It is recommended to {\bfseries{NOT USE}} implicit conversions {\bfseries{FROM}} a JSON value. You can find more details about this recommendation \href{https://www.github.com/nlohmann/json/issues/958}{\texttt{ here}}. You can switch off implicit conversions by defining {\ttfamily JSON\+\_\+\+USE\+\_\+\+IMPLICIT\+\_\+\+CONVERSIONS} to {\ttfamily 0} before including the {\ttfamily json.\+hpp} header. When using CMake, you can also achieve this by setting the option {\ttfamily JSON\+\_\+\+Implicit\+Conversions} to {\ttfamily OFF}.

That\textquotesingle{}s all! When calling the {\ttfamily json} constructor with your type, your custom {\ttfamily to\+\_\+json} method will be automatically called. Likewise, when calling {\ttfamily template get\texorpdfstring{$<$}{<}your\+\_\+type\texorpdfstring{$>$}{>}()} or {\ttfamily get\+\_\+to(your\+\_\+type\&)}, the {\ttfamily from\+\_\+json} method will be called.

Some important things\+:


\begin{DoxyItemize}
\item Those methods {\bfseries{MUST}} be in your type\textquotesingle{}s namespace (which can be the global namespace), or the library will not be able to locate them (in this example, they are in namespace {\ttfamily ns}, where {\ttfamily person} is defined).
\item Those methods {\bfseries{MUST}} be available (e.\+g., proper headers must be included) everywhere you use these conversions. Look at \href{https://github.com/nlohmann/json/issues/1108}{\texttt{ issue 1108}} for errors that may occur otherwise.
\item When using {\ttfamily template get\texorpdfstring{$<$}{<}your\+\_\+type\texorpdfstring{$>$}{>}()}, {\ttfamily your\+\_\+type} {\bfseries{MUST}} be \href{https://en.cppreference.com/w/cpp/named_req/DefaultConstructible}{\texttt{ Default\+Constructible}}. (There is a way to bypass this requirement described later.)
\item In function {\ttfamily from\+\_\+json}, use function \href{https://json.nlohmann.me/api/basic_json/at/}{\texttt{ {\ttfamily at()}}} to access the object values rather than {\ttfamily operator\mbox{[}\mbox{]}}. In case a key does not exist, {\ttfamily at} throws an exception that you can handle, whereas {\ttfamily operator\mbox{[}\mbox{]}} exhibits undefined behavior.
\item You do not need to add serializers or deserializers for STL types like {\ttfamily std\+::vector}\+: the library already implements these.
\end{DoxyItemize}\hypertarget{md_build_2dt__core_2__deps_2nlohmann__json-src_2README_autotoc_md1779}{}\doxyparagraph{\texorpdfstring{Simplify your life with macros}{Simplify your life with macros}}\label{md_build_2dt__core_2__deps_2nlohmann__json-src_2README_autotoc_md1779}

Though it\textquotesingle{}s 2023 already, the support for C++11 is still a bit sparse. Currently, the following compilers are known to work\+:


\begin{DoxyItemize}
\item GCC 4.\+8 -\/ 12.\+0 (and possibly later)
\item Clang 3.\+4 -\/ 15.\+0 (and possibly later)
\item Apple Clang 9.\+1 -\/ 13.\+1 (and possibly later)
\item Intel C++ Compiler 17.\+0.\+2 (and possibly later)
\item Nvidia CUDA Compiler 11.\+0.\+221 (and possibly later)
\item Microsoft Visual C++ 2015 / Build Tools 14.\+0.\+25123.\+0 (and possibly later)
\item Microsoft Visual C++ 2017 / Build Tools 15.\+5.\+180.\+51428 (and possibly later)
\item Microsoft Visual C++ 2019 / Build Tools 16.\+3.\+1+1def00d3d (and possibly later)
\item Microsoft Visual C++ 2022 / Build Tools 19.\+30.\+30709.\+0 (and possibly later)
\end{DoxyItemize}

I would be happy to learn about other compilers/versions.

Please note\+:


\begin{DoxyItemize}
\item GCC 4.\+8 has a bug \href{https://gcc.gnu.org/bugzilla/show_bug.cgi?id=57824}{\texttt{ 57824}})\+: multiline raw strings cannot be the arguments to macros. Don\textquotesingle{}t use multiline raw strings directly in macros with this compiler.
\item Android defaults to using very old compilers and C++ libraries. To fix this, add the following to your {\ttfamily Application.\+mk}. This will switch to the LLVM C++ library, the Clang compiler, and enable C++11 and other features disabled by default.


\begin{DoxyCode}{0}
\DoxyCodeLine{APP\_STL\ :=\ c++\_shared}
\DoxyCodeLine{NDK\_TOOLCHAIN\_VERSION\ :=\ clang3.6}
\DoxyCodeLine{APP\_CPPFLAGS\ +=\ -\/frtti\ -\/fexceptions}

\end{DoxyCode}


The code compiles successfully with \href{https://developer.android.com/ndk/index.html?hl=ml}{\texttt{ Android NDK}}, Revision 9 -\/ 11 (and possibly later) and \href{https://www.crystax.net/en/android/ndk}{\texttt{ CrystaX\textquotesingle{}s Android NDK}} version 10.
\item For GCC running on Min\+GW or Android SDK, the error `\textquotesingle{}to\+\_\+string' is not a member of \textquotesingle{}std\textquotesingle{}{\ttfamily (or similarly, for}strtod{\ttfamily or}strtof{\ttfamily ) may occur. Note this is not an issue with the code, but rather with the compiler itself. On Android, see above to build with a newer environment. For Min\+GW, please refer to \mbox{[}this site\mbox{]}(\href{https://tehsausage.com/mingw-to-string}{\texttt{ https\+://tehsausage.\+com/mingw-\/to-\/string}}) and \mbox{[}this discussion\mbox{]}(\href{https://github.com/nlohmann/json/issues/136}{\texttt{ https\+://github.\+com/nlohmann/json/issues/136}}) for information on how to fix this bug. For Android NDK using}APP\+\_\+\+STL \+:= gnustl\+\_\+static\`{}, please refer to \href{https://github.com/nlohmann/json/issues/219}{\texttt{ this discussion}}.
\item Unsupported versions of GCC and Clang are rejected by {\ttfamily \#error} directives. This can be switched off by defining {\ttfamily JSON\+\_\+\+SKIP\+\_\+\+UNSUPPORTED\+\_\+\+COMPILER\+\_\+\+CHECK}. Note that you can expect no support in this case.
\end{DoxyItemize}

The library supports {\bfseries{Unicode input}} as follows\+:


\begin{DoxyItemize}
\item Only {\bfseries{UTF-\/8}} encoded input is supported which is the default encoding for JSON according to \href{https://tools.ietf.org/html/rfc8259.html\#section-8.1}{\texttt{ RFC 8259}}.
\item {\ttfamily std\+::u16string} and {\ttfamily std\+::u32string} can be parsed, assuming UTF-\/16 and UTF-\/32 encoding, respectively. These encodings are not supported when reading from files or other input containers.
\item Other encodings such as Latin-\/1 or ISO 8859-\/1 are {\bfseries{not}} supported and will yield parse or serialization errors.
\item \href{https://www.unicode.org/faq/private_use.html\#nonchar1}{\texttt{ Unicode noncharacters}} will not be replaced by the library.
\item Invalid surrogates (e.\+g., incomplete pairs such as {\ttfamily \textbackslash{}u\+DEAD}) will yield parse errors.
\item The strings stored in the library are UTF-\/8 encoded. When using the default string type ({\ttfamily std\+::string}), note that its length/size functions return the number of stored bytes rather than the number of characters or glyphs.
\item When you store strings with different encodings in the library, calling \href{https://json.nlohmann.me/api/basic_json/dump/}{\texttt{ {\ttfamily dump()}}} may throw an exception unless {\ttfamily json\+::error\+\_\+handler\+\_\+t\+::replace} or {\ttfamily json\+::error\+\_\+handler\+\_\+t\+::ignore} are used as error handlers.
\item To store wide strings (e.\+g., {\ttfamily std\+::wstring}), you need to convert them to a UTF-\/8 encoded {\ttfamily std\+::string} before, see \href{https://json.nlohmann.me/home/faq/\#wide-string-handling}{\texttt{ an example}}.
\end{DoxyItemize}\hypertarget{md_build_2dt__core_2__deps_2nlohmann__json-src_2README_autotoc_md1803}{}\doxysubsubsection{\texorpdfstring{Comments in JSON}{Comments in JSON}}\label{md_build_2dt__core_2__deps_2nlohmann__json-src_2README_autotoc_md1803}
This library does not support comments by default. It does so for three reasons\+:


\begin{DoxyEnumerate}
\item Comments are not part of the \href{https://tools.ietf.org/html/rfc8259}{\texttt{ JSON specification}}. You may argue that {\ttfamily //} or {\ttfamily /\texorpdfstring{$\ast$}{*} \texorpdfstring{$\ast$}{*}/} are allowed in Java\+Script, but JSON is not Java\+Script.
\item This was not an oversight\+: Douglas Crockford \href{https://plus.google.com/118095276221607585885/posts/RK8qyGVaGSr}{\texttt{ wrote on this}} in May 2012\+:
\end{DoxyEnumerate}

\begin{quote}
I removed comments from JSON because I saw people were using them to hold parsing directives, a practice which would have destroyed interoperability. I know that the lack of comments makes some people sad, but it shouldn\textquotesingle{}t. \end{quote}
\begin{quote}
Suppose you are using JSON to keep configuration files, which you would like to annotate. Go ahead and insert all the comments you like. Then pipe it through JSMin before handing it to your JSON parser. \end{quote}

\begin{DoxyEnumerate}
\item It is dangerous for interoperability if some libraries would add comment support while others don\textquotesingle{}t. Please check \href{https://tools.ietf.org/html/draft-iab-protocol-maintenance-01}{\texttt{ The Harmful Consequences of the Robustness Principle}} on this.
\end{DoxyEnumerate}

However, you can pass set parameter {\ttfamily ignore\+\_\+comments} to true in the {\ttfamily parse} function to ignore {\ttfamily //} or {\ttfamily /\texorpdfstring{$\ast$}{*} \texorpdfstring{$\ast$}{*}/} comments. Comments will then be treated as whitespace.\hypertarget{md_build_2dt__core_2__deps_2nlohmann__json-src_2README_autotoc_md1804}{}\doxysubsubsection{\texorpdfstring{Order of object keys}{Order of object keys}}\label{md_build_2dt__core_2__deps_2nlohmann__json-src_2README_autotoc_md1804}

If you find that a parsing program with this library does not release memory, please consider the following case, and it may be unrelated to this library.

{\bfseries{Your program is compiled with glibc.}} There is a tunable threshold that glibc uses to decide whether to actually return memory to the system or whether to cache it for later reuse. If in your program you make lots of small allocations and those small allocations are not a contiguous block and are presumably below the threshold, then they will not get returned to the OS. \begin{DoxyItemize}
\item The code contains numerous debug {\bfseries{assertions}} which can be switched off by defining the preprocessor macro {\ttfamily NDEBUG}, see the \href{https://en.cppreference.com/w/cpp/error/assert}{\texttt{ documentation of {\ttfamily assert}}}. In particular, note \href{https://json.nlohmann.me/api/basic_json/operator\%5B\%5D/}{\texttt{ {\ttfamily operator\mbox{[}\mbox{]}}}} implements {\bfseries{unchecked access}} for const objects\+: If the given key is not present, the behavior is undefined (think of a dereferenced null pointer) and yields an \href{https://github.com/nlohmann/json/issues/289}{\texttt{ assertion failure}} if assertions are switched on. If you are not sure whether an element in an object exists, use checked access with the \href{https://json.nlohmann.me/api/basic_json/at/}{\texttt{ {\ttfamily at()} function}}. Furthermore, you can define {\ttfamily \doxylink{macro__scope_8hpp_a69f131cff49da1989667220173fbeae6}{JSON\+\_\+\+ASSERT(x)}} to replace calls to {\ttfamily assert(x)}.
\item As the exact number type is not defined in the \href{https://tools.ietf.org/html/rfc8259.html}{\texttt{ JSON specification}}, this library tries to choose the best fitting C++ number type automatically. As a result, the type {\ttfamily double} may be used to store numbers which may yield \href{https://github.com/nlohmann/json/issues/181}{\texttt{ {\bfseries{floating-\/point exceptions}}}} in certain rare situations if floating-\/point exceptions have been unmasked in the calling code. These exceptions are not caused by the library and need to be fixed in the calling code, such as by re-\/masking the exceptions prior to calling library functions.
\item The code can be compiled without C++ {\bfseries{runtime type identification}} features; that is, you can use the {\ttfamily -\/fno-\/rtti} compiler flag.
\item {\bfseries{Exceptions}} are used widely within the library. They can, however, be switched off with either using the compiler flag {\ttfamily -\/fno-\/exceptions} or by defining the symbol {\ttfamily JSON\+\_\+\+NOEXCEPTION}. In this case, exceptions are replaced by {\ttfamily abort()} calls. You can further control this behavior by defining {\ttfamily JSON\+\_\+\+THROW\+\_\+\+USER} (overriding {\ttfamily throw}), {\ttfamily JSON\+\_\+\+TRY\+\_\+\+USER} (overriding {\ttfamily try}), and {\ttfamily JSON\+\_\+\+CATCH\+\_\+\+USER} (overriding {\ttfamily catch}). Note that {\ttfamily JSON\+\_\+\+THROW\+\_\+\+USER} should leave the current scope (e.\+g., by throwing or aborting), as continuing after it may yield undefined behavior. Note the explanatory \href{https://en.cppreference.com/w/cpp/error/exception/what}{\texttt{ {\ttfamily what()}}} string of exceptions is not available for MSVC if exceptions are disabled, see \href{https://github.com/nlohmann/json/discussions/2824}{\texttt{ \#2824}}.
